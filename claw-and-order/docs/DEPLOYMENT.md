# Claw & Order deployment readiness

This release has two repositories. `Operation-Claw-and-Order` receives Kali reporter events, scores them, and sends Discord alerts. `c3claw` shows the team topology and imports scored events from the backend export. It can also import distinct `[OCRT]` telemetry from Discord. Do not send the same logical event through both sources: their source IDs differ and it would be counted twice.

The following gates are for a **staging rehearsal before production**. Record the result, owner, date, and rollback artifact for each gate. A local PostgreSQL smoke run is useful evidence, but does not replace a test against the production sized database and live Discord configuration.

Student enrollment is now part of this release. Follow [STUDENT-ENROLLMENT.md](STUDENT-ENROLLMENT.md), complete the faculty [role definitions](ROLE-DEFINITIONS.md), and use the `../deploy/` examples. Apply the new backend enrollment tables/revision seed and dashboard `enrollment_snapshots` migration before starting updated processes. API and enrollment worker are separate processes; include both pools in the PostgreSQL connection budget. The worker needs its own bot token and the API/worker must use the same reviewed policy hash.

Before promotion, a staff pilot must verify two classes, a student in both classes, an unassigned student, a team transfer and withdrawal, private channel isolation, expired/reissued codes, permission/network failure recovery and accurate dashboard counts. Email delivery needs its own reviewed institutional SMTP pilot. If any gate fails, pause invitations, preserve queues/receipts, repair and apply a reviewed reconciliation. No student responsibility labels or permissions are guessed from spreadsheets or student ideas.

## Release sequence

1. Freeze a commit SHA and record the current backend image, dashboard release, config, schema, and a fresh backup. Run both CI workflows and verify a restore on an isolated database. The backend image installs pinned versions from `requirements.lock`; refresh that file deliberately when dependencies change.
2. Reconcile the real roster. `scripts/provision_tokens.py` adds teams without rotating existing tokens; deliver each new reporter config to its team securely. Make dashboard inventory IDs identical. Populate `reporter/technique_map.json` with actual tool patterns.
3. Rehearse on a production sized PostgreSQL clone. From `claw-and-order/`, run `python -m backend.migrate` with `DATABASE_URL=postgresql+asyncpg://...`. For `c3claw`, run `npm run migrate`; its Heroku `Procfile` runs this in release phase. Confirm the migrations are idempotent and the dedupe indexes are valid. These commands intentionally do not run on web process startup in production.
4. Deploy the backend image from the repository root (`docker build -t claw-backend:<sha> .`). Set `APP_ENV=production`, `DATABASE_URL`, `ADMIN_SECRET`, `EVENT_EXPORT_SECRET`, and optional `DISCORD_WEBHOOK_URL` (shared instructor channel) or `DISCORD_WEBHOOKS_FILE`/`DISCORD_WEBHOOKS_JSON` (class routes; see `docs/discord-integration-guide.md`), `CORS_ORIGINS`, `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`. Keep the export secret distinct from the admin secret. Run **one** web worker because the Discord sender and watchdog live in that process. Legacy bot delivery remains available through `DISCORD_TOKEN` and `DISCORD_CHANNEL_ID`; choose one delivery mode. Webhook mode requires the `discord_webhook_deliveries` and `discord_webhook_destinations` tables from the release migration. The default pool maximum is 7 connections. The database URL must use the `postgresql+asyncpg://` scheme. After the old backend stops, rerun `python -m backend.migrate` before starting the dashboard importer: this backfills any events the old version wrote between the first migration and cutover.
5. Deploy the dashboard after the backend export is live. Set `NODE_ENV=production`, `DATABASE_URL`, `EVENT_API_KEY`, optional `VITE_API_URL` before frontend build (empty uses the same origin), `BACKEND_EXPORT_URL` (backend base URL), and `BACKEND_EXPORT_SECRET` (same value as backend `EVENT_EXPORT_SECRET`). Set `TOPOLOGY_JSON`/`TOPOLOGY_FILE`. If Discord import is used, set `DISCORD_BOT_TOKEN` and explicit `ALLOWED_CHANNELS`; decide `DISCORD_INITIAL_BACKFILL` before first start. Leave the bot disabled if Discord carries the same events as the backend export.
6. Send one sentinel event per team through its reporter. Compare backend receipt, dashboard `source_id=backend:<event_id>`, dashboard event count, topology card, and timestamps. Restart each app once and verify counts remain unchanged. Stop the backend briefly in staging: dashboard health must become 503, then recover to 200 with its cursor intact.
7. Test each real Discord webhook destination with the non-posting preflight and a controlled staging alert. Confirm per-class routing, receipt persistence, retries, and `discord_webhook_failures=0`. For an optional Discord telemetry reader, verify bot permissions, Message Content intent, one accepted `[OCRT]` example, one malformed example recorded as a rejection, and catch-up after reconnect. Confirm the backend outbox has no old pending rows.
8. Run the scale/restore/rollback rehearsal, then enable monitoring and schedule operators for the first exercise window. Promote only when every gate has evidence.

The staging load driver is `python scripts/load_rehearsal.py --url <backend> --team-id <test-team> --token <test-token> --target-ip <team-CIDR-IP> --rate <events-per-second> --duration 3600 --staging-write`. It emits unique `source_id` values, uses phase-one `port_scan` with a failure result to avoid scoring milestones, and prints accepted count plus p95/p99 request latency. Use a dedicated staging team and token. Run a short 5× burst with the same command and a higher `--rate`; compare backend and dashboard counts after catch-up. A backend rate limit of 300 events/minute per team applies, so provision enough staging teams or revise the test design for a total rate above that limit.

## Data checks and signals

- Backend `/api/health`: `db=ok`, `discord=webhook_ready` (or legacy `connected`) when configured, `discord_pending=0` after drain, `discord_oldest_pending_seconds<120`, and `dashboard_pending=0` after export catch-up. It returns 503 if DB fails, Discord is configured but disconnected, or a configured Discord/dashboard delivery is older than 120 s.
- Dashboard `/api/health`: `persistence=postgres`, `backend_sync.last_error=null`, `backend_sync.pending_events=0` after catch-up, and `discord.failed_channels=0` when configured. It returns 503 on failed/stale sync or more than 1000 pending events. `cursor` is an observational high-water mark, not the delivery gate.
- Backend reconciliation: compare `SELECT team_id, COUNT(*) FROM events GROUP BY team_id` with `SELECT team_id, event_count FROM team_event_counts`. Run full scans off peak on a production sized clone.
- Dashboard reconciliation: compare `SELECT team_id, COUNT(*) FROM events GROUP BY team_id` with `team_status.event_count`. Compare backend non-heartbeat event totals with dashboard rows where `source_id LIKE 'backend:%'` after the backend `dashboard_outbox` pending count reaches zero. Investigate duplicate logical events from Discord separately. Event IDs can commit out of order; the queue plus acknowledgement prevents an ID cursor from skipping a late commit.
- Reporter permanent 400/403/409/413/422 responses move full payloads to `retry*.rejected.jsonl` and continue. A 401, 429, 5xx, or transport failure stays retryable; a 401 needs token repair. Alert on rejected-file growth and disk space.
- Newly provisioned team tokens are 256-bit random values stored as SHA-256 verifiers and checked in constant time. Existing bcrypt verifiers upgrade after the first valid request without rotating the token. The first request for a legacy team may be slower; rehearse before peak traffic.
- The outbox is at least once. A process crash after Discord accepts a message but before DB marks it sent can produce a duplicate; reconcile the message with its outbox row.

## Rollback

Return app images/commits to the recorded prior versions only after checking schema compatibility. Stop the dashboard backend importer by removing `BACKEND_EXPORT_URL` and `BACKEND_EXPORT_SECRET` if it misbehaves; retain `dashboard_outbox`, `backend_sync_cursors`, and all event rows. The backend marks an event delivered only after the dashboard stores and acknowledges it. Keep reporter retry buffers and backend outbox rows intact. If a migration changes data incorrectly, stop writers, restore the verified backup to a separate database, compare counts/queues, then cut over. Record actual data loss and recovery time. Do not wipe event tables to make a deploy pass.

## Local rehearsal evidence (2026-11-02)

On isolated PostgreSQL 16 with one backend container and one dashboard process, a scored event reached the dashboard in the next five-second poll with its original timestamp. Stopping the backend made dashboard health return 503; restart returned it to 200 without a duplicate. Both migrations reran cleanly. A 20-event, 10/s staging load found the synchronous bcrypt bottleneck at about 6.8 s p95. After the verifier upgrade, the first 20-event run was 439 ms p95 and the next was 20 ms p95 / 36 ms p99. Reconciliation then found one of 61 events missing because its lower ID committed after the old cursor advanced. The transactional `dashboard_outbox` migration replayed all 61; the dashboard stored the missing event and acknowledged the queue to zero. A subsequent event 62 imported once. A further concurrent 20-event run reconciled at 82 backend events, 82 dashboard backend rows, and zero pending queue rows. These small local runs establish behavior, not production capacity.
